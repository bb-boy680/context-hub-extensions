# Qoder CLI

Context Hub extension for Qoder CLI. Skills use the default `~/.qoder/skills` and project `.qoder/skills` directories.

MCP declarations are read from user `~/.qoder/settings.json`, project `.mcp.json`, `.qoder/settings.json`, and `.qoder/settings.local.json`. New installations default to user settings or project `.mcp.json`. The other two project files remain available for existing declarations. Project settings depend on Qoder's project trust behavior. Custom `QODER_CONFIG_DIR` roots for these assets are not supported.

Commands, rules and agents can be delivered to the user or project `.qoder` directory. Rules use Qoder's default always-active Markdown behavior; global instructions are placed in a marked section of `~/.qoder/AGENTS.md`. Project `AGENTS.md` is managed by the shared workspace provider. Conflict precedence belongs to Qoder.

The extension contributes `.qoder-plugin/plugin.json` to the Hub's native manifest collection. The Hub currently reads generic name, version and description; this does not provide a complete parser for Qoder-specific component paths. The extension also registers a file-based installer for Qoder's user, project and local plugin scopes, using the native `installed_plugins_v2.json` registry, `cache/local/<name>/<version>` and `enabledPlugins` settings.

The official [`@qoder-ai/qodercli` 1.1.81 JavaScript distribution](https://unpkg.com/@qoder-ai/qodercli@1.1.81/bundle/qodercli.js) was inspected as text without execution (35,653,383 bytes; SHA-256 base64 `3Ku8rs4cBoPuSSmsfAzw6gC76k0xn1q+qughYIi5iI8=`). It defines `plugins/installed_plugins_v2.json` as `{version: 2, plugins: {id: [record]}}`; each record has `scope` and `installPath`, with optional `projectPath`, `version`, `installedAt` and other fields. Local installs use `name@local`, copy into `cache/local/<name>/<version>` and use `local` when the manifest has no version. The plugin state root can also be overridden with `QODER_PLUGIN_CACHE_DIR`. Project records use the manager's working directory, while applicability includes descendants. A record is removed only for the requested scope and project; cached data is removed only when the ID has no remaining records. The native install copy excludes top-level `.git`, `node_modules`, `.env` and `.env.*`, and handles symlinks specially.

The checked-in `__test__/fixtures/registry-v2.json` models the `bTe`/`jCu` schema and `N7` scope/project identity in that exact 1.1.81 distribution; paths and names are synthetic. The same bundle's `kCu`, `gme` and `JTe` accept dependency names or `{name, marketplace}` objects. The unregistered installer preflight checks already-installed, enabled dependencies without downloading them. The fixture is a test input, not evidence of a real installation.

Those findings describe that pinned distribution, not a complete safe Hub transaction. Ownership of existing `name@local` records and cache copies cannot be inferred from the native record, which has no Hub provenance; the extension keeps a sidecar with the client roots, installation identity and directory snapshot. It registers only entries it can prove it owns; other entries stay read-only. The installer uses the shared journalled transaction and the shared file guard, whose journal stores file references and transaction metadata rather than configuration contents; an interrupted transaction requires manual inspection and recovery. To avoid copying potential credentials, installation will reject a package containing a nested `.env` or `.env.*` file before writing; remove that file from the package and retry. On Windows, changes to an existing settings file are refused until the host can preserve its ACL; this prevents replacing a file that may contain credentials with one whose inherited ACL is unknown. Dependency resolution and runtime loading have not been independently verified. No CLI fallback is used.

The `engines.contextHub` range is the development baseline; the native manifest contract, journalled plugin transactions and the read-only file guard require the current unreleased host API. Before publishing, set the minimum version to the first actual release that provides them. Qoder CLI paths and behavior were checked against [official documentation](https://docs.qoder.com/cli/plugins-reference) on 2026-11-03. Qoder Desktop/IDE, legacy formats and asset-level custom configuration roots are outside this extension's current scope.
